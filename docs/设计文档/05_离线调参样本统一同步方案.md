# 离线调参样本统一同步方案

## 一、背景

当前北交所新股估值框架中，估值调参与申购资金调参已经共享一部分样本基础，但落盘形态和刷新入口仍然分散：

- 估值调参使用 `data/offline_tuning/replay_dataset.json` 和 `data/offline_tuning/replay_items/*.json`。
- 首日成交均价使用 `data/offline_tuning/listing_average_prices.json` 缓存。
- 申购资金调参使用 `data/offline_tuning/subscription_history_sample.csv`。
- 手工分档标签使用 `data/offline_tuning/subscription_ladder_labels.csv`。
- 新上市新股的首日分时走势由 `tools/add_new_ipo_intraday_cache.py` 刷新到 `首日分时走势/`。

2026-06-29 至 2026-06-30 的跨机器参数集和样本集合并暴露出一个问题：同一只新股的估值 replay、申购 history、手工标签可能分别在不同机器上更完整，合并时需要人工判断。后续应统一刷新入口和样本元数据，让“是否可用、来自哪里、是否人工择优”更容易检查。

## 二、目标

本方案第一阶段目标：

- 保留现有文件格式，避免大规模迁移。
- 新增统一同步脚本，串联估值 replay、申购 history、手工标签同步。
- 生成机器可读的同步报告，用于后续跨机器合并和人工复核。
- 将现有“刷新首日走势”bat 改造成菜单入口：
  - 选项 1：刷新新股首日走势。
  - 选项 2：刷新新上市新股数据。

本方案暂不做：

- 不把 JSON replay 和 CSV history 合并成一个大文件。
- 不删除现有调参入口中的自动刷新逻辑。
- 不立刻拆分 `subscription_ladder_labels.csv` 的人工列和自动列。
- 不把公告 PDF 纳入跨机器提交资产。

## 三、当前数据边界

### 估值 replay 数据

主文件：

- `data/offline_tuning/replay_dataset.json`

单样本缓存：

- `data/offline_tuning/replay_items/{security_code}.json`

特征：

- 适合 JSON，因为字段包含嵌套结构，如可比公司快照、老股提取元数据、首日均价来源等。
- `replay_dataset.json` 是聚合快照，调参和候选复核主要读取它。
- `replay_items/*.json` 是增量构建缓存，包含 `record_signature` 和 `pdf_signature`。

### 首日均价缓存

文件：

- `data/offline_tuning/listing_average_prices.json`

特征：

- 从 `首日分时走势/*.csv` 计算首日成交均价。
- 通过 CSV 文件签名和计算版本判断缓存是否可复用。

### 申购 history 数据

文件：

- `data/offline_tuning/subscription_history_sample.csv`

特征：

- 从 replay item 和公告 PDF 解析结果派生。
- 生成时会读取旧 CSV，并用质量评分保留更完整的旧行。
- 适合 CSV，因为调参指标、人工复核和差异比较更直观。

### 手工分档标签

文件：

- `data/offline_tuning/subscription_ladder_labels.csv`

特征：

- 包含自动上下文列和人工列。
- 自动列包括简称、申购日期、发行价、网上发行股数、顶格申购金额。
- 人工列包括 `manual_ladder` 和 `manual_note`。
- 同步时应刷新自动列，但必须保留人工列。

## 四、统一同步流程

新增脚本：

- `tools/sync_offline_tuning_dataset.py`

默认执行顺序：

1. 读取 `策略参数.txt`。
2. 检查并按需刷新估值 replay 数据集。
3. 保存或复用 `replay_items/*.json`。
4. 保存 `replay_dataset.json` 聚合快照。
5. 从 replay 数据集派生 `subscription_history_sample.csv`。
6. 同步 `subscription_ladder_labels.csv`，保护人工列。
7. 生成 `data/offline_tuning/sample_manifest.json`。

脚本默认不刷新 `首日分时走势/*.csv`，因为该动作已经由独立选项负责。推荐人工操作顺序：

1. 先执行 bat 选项 1，刷新新股首日走势。
2. 再执行 bat 选项 2，刷新新上市新股数据。

## 五、同步报告设计

新增文件：

- `data/offline_tuning/sample_manifest.json`

建议 schema：

```json
{
  "schema": "offline_tuning_sample_manifest_v1",
  "generated_at": "YYYY-MM-DD HH:MM:SS",
  "paths": {
    "dataset": "...",
    "history": "...",
    "ladder_labels": "..."
  },
  "summary": {
    "intraday_csv_count": 0,
    "replay_item_count": 0,
    "replay_dataset_count": 0,
    "subscription_history_count": 0,
    "ladder_label_count": 0
  },
  "samples": [
    {
      "security_code": "920000",
      "in_intraday_csv": true,
      "in_replay_dataset": true,
      "has_replay_item": true,
      "in_subscription_history": true,
      "in_ladder_labels": true,
      "method1_replay_available": true,
      "history_quality_score": 0,
      "model_ready": true,
      "manual_ladder_label_ready": true
    }
  ]
}
```

第一阶段的 manifest 只记录已有信息，不改变现有业务文件。

## 六、bat 入口设计

改造文件：

- `添加新股首日走势.bat`

菜单：

```bat
1. 刷新新股首日走势
2. 刷新新上市新股数据
```

选项 1：

- 调用 `python -u tools\add_new_ipo_intraday_cache.py`

选项 2：

- 调用 `python -u tools\sync_offline_tuning_dataset.py`

保留：

- UTF-8 控制台设置。
- 脚本执行后暂停。
- 非零退出码向 bat 外层返回。

## 七、后续演进

第二阶段建议：

- 将估值调参和申购调参入口中的自动刷新逻辑改为调用统一同步模块，而不是各自拼接刷新流程。
- 在 manifest 中记录 history 行是否来自旧行质量保护。
- 在 replay item 中增加跨机器共享元数据，例如 `snapshot_origin`、`manual_merge_note`、`rebuildable_on_current_machine`。

第三阶段建议：

- 拆分 `subscription_ladder_labels.csv`：
  - 纯人工输入：`subscription_ladder_manual_labels.csv`
  - 自动生成视图：`subscription_ladder_labels.csv`
- 将跨机器合并流程改为优先比较 manifest 和质量摘要，再比较具体 JSON/CSV。

## 八、第二阶段落地：统一调用与公告补取

本阶段把统一同步脚本从独立命令提升为可复用模块，调参相关入口统一调用同一套编排函数：

- `tools/sync_offline_tuning_dataset.py::sync_offline_tuning_dataset()`
- `tools/tune_params.py` 的 replay 数据集刷新委托统一模块。
- `tools/tune_subscription_prediction.py` 的调参前刷新委托统一模块。
- `tools/manual_tune_prompt.py` 的调参前样本刷新委托统一模块。

保留边界：

- 正式单只新股估值主流程 `code/bse_ipo_valuation.py` 仍独立下载、解析目标股票公告和估值数据。
- 首日分时走势仍由 bat 选项 1 刷新。
- 用户手工填写的阶梯申购金额仍保存在 `subscription_ladder_labels.csv` 的人工列中。

bat 选项 2 的刷新范围：

1. 估值 replay 聚合数据集 `data/offline_tuning/replay_dataset.json`。
2. 估值 replay 单样本缓存 `data/offline_tuning/replay_items/*.json`。
3. 申购 history `data/offline_tuning/subscription_history_sample.csv`。
4. 手工阶梯标签上下文 `data/offline_tuning/subscription_ladder_labels.csv`。
5. 样本 manifest `data/offline_tuning/sample_manifest.json`。
6. 待重试标记 `data/offline_tuning/deferred_listing_data_codes.json`。

公告下载与解析策略：

- 选项 2 默认打开缺失公告补取。
- 当发行公告或发行结果公告缺失时，调用 `build_subscription_history.build_subscription_history_table()` 的 `download_missing_issue=True` 与 `download_missing_result=True`。
- 下载后立即解析所需申购字段，并继续沿用 history 旧行质量保护，避免低质量新解析覆盖旧高质量结果。
- 可用 `--no-download-missing-announcements` 显式关闭公告下载，仅解析本地已有 PDF。

重试策略与选项 1 保持一致：

- 本次仍未取到公告、解析报错或字段未齐的代码写入 `deferred_listing_data_codes.json`。
- 下次执行选项 2 时先读取待重试标记，并重新尝试公告下载和解析。
- 如果重试后字段齐备，则该代码从待重试标记中移除。
- 如果代码暂时不在当前 history 中，则保留 `pending_code_not_in_current_history`，避免无声丢失待处理状态。
