## 五、进一步检查结果

实际数据规模：

- `replay_dataset.json`：`available_count=35`，`sample_codes=35`，`requested_codes=35`。
- `data/offline_tuning/replay_items/*.json`：35 个单样本缓存文件。
- `subscription_history_sample.csv`：35 行。
- `subscription_ladder_labels.csv`：38 行。
- `首日分时走势/*.csv`：35 个代码，当前与 replay 数据集代码列表一致。
- 手工标签多出的代码：`920136`、`920193`、`920222`，这些代码当前只存在于标签表，不在 replay/history 样本表。

估值 replay 的存储特点：

- 聚合文件 `replay_dataset.json` 直接内嵌 `items`，调参和候选复核主要读取该文件。
- 单样本缓存 `replay_items/*.json` 是 wrapper 结构，包含：
  - `schema`
  - `cache_version`
  - `generated_at`
  - `code`
  - `listing_date`
  - `record_signature`
  - `pdf_signature`
  - `item`
- 构建 replay 数据集时，会按以下顺序复用：
  - 优先读取单样本缓存，要求 `record_signature` 和 `pdf_signature` 完全匹配。
  - 如果单样本缓存未命中，但旧聚合数据集中存在同代码且发行记录签名匹配，则复用旧聚合条目。
  - 如果旧条目缺少新版首日均价字段，则尝试升级旧条目。
  - 都不可用时才重新构建样本。
- replay 同步检查主要比较本地 `首日分时走势/*.csv` 代码列表、回看月份和缓存版本；它不检查每个单样本 wrapper 与聚合 `items` 是否逐字段一致。

申购历史样本的存储特点：

- `subscription_history_sample.csv` 是从 replay item 派生的训练表，不是原始事实源。
- 派生过程会再次读取本地 `公告文件/`，解析发行公告、发行结果公告、上市公告等文件。
- 生成新行后，会读取旧 `subscription_history_sample.csv`，用 `_row_quality_score()` 做质量保护：旧行质量更高时保留旧行。
- 这能避免“本机缺 PDF 或公告解析失败”时覆盖掉已有高质量申购样本。
- 代价是：CSV 中某些字段可能来自旧运行环境，而不是当前 replay/PDF 环境即时可复现的结果。

手工分档标签的存储特点：

- `subscription_ladder_labels.csv` 同时包含自动补齐列和人工列：
  - 自动列：简称、申购日期、发行价、网上发行股数、顶格申购金额。
  - 人工列：`manual_ladder`、`manual_note`。
- 同步标签时会用最新样本刷新自动列，但保留人工列。
- 标签文件支持 `utf-8-sig`、`utf-8`、`gb18030`、`cp936` 读取，并在同步后标准化为 UTF-8。
- 调参视图会把标签行合并到历史样本中，因此标签表中尚未进入 replay/history 的代码，也可能出现在申购调参评估视图里。

## 六、阶段性结论：需要统一，但不是合成一个物理文件

需要统一的部分：

- 统一样本清单：明确每个代码是否进入估值 replay、申购 history、手工标签、候选复核。
- 统一刷新入口：估值和申购都应通过同一个“离线调参样本同步”命令编排，而不是分别在两个调参入口里各自尝试刷新。
- 统一元数据：每个样本应记录来源、更新时间、是否依赖本机 PDF、是否依赖本机分时 CSV、是否可提交跨机器共享。
- 统一质量规则：申购 history 当前有质量保护，估值 replay 聚合和单样本缓存也需要类似的冲突/择优说明。

不建议统一成一个大文件的部分：

- 估值 replay item 字段多且嵌套深，适合 JSON。
- 申购 history 是调参表格，适合 CSV 审阅和回归对比。
- 手工分档标签面向人工维护，继续保留 CSV 更合适。
- 候选参数集是另一类资产，不应混入样本事实数据。

更合理的统一方式：

- 保留现有文件类型，但增加一个样本 manifest 或同步报告，作为统一入口的产物。
- 让 `replay_dataset.json` 成为估值调参的聚合快照，而不是唯一事实源。
- 让 `replay_items/*.json` 成为每个代码的估值快照缓存。
- 让 `subscription_history_sample.csv` 明确标记为派生训练表，由统一命令生成和质量合并。
- 将 `subscription_ladder_labels.csv` 的人工列边界进一步收窄，后续可以考虑拆出 `subscription_ladder_manual_labels.csv`，自动列由同步命令生成。

## 七、当前设计暴露的具体风险点

### 1. replay cache 的 PDF 签名和跨机器共享目标存在张力

单样本 replay cache 当前使用本机 PDF 文件签名做复用判断：

- `listing`
- `old_shares`
- `comparables`

但 2026-06-29 已确认公告 PDF 不作为跨机器迁移资产。这样会产生两类问题：

- 如果坚持用本机 PDF 签名判定缓存是否有效，跨机器提交的 replay cache 到另一台机器后可能因为缺 PDF 而无法复用。
- 如果为了跨机器共享而保留缓存 item，但本机没有对应 PDF，又缺少“该 item 的可比公司/老股数据来自哪台机器、哪份文件、是否人工择优”的元数据，后续很难判断该条目是否应覆盖或保留。

本轮 `920072` 就属于这类样本：本地更完整的 replay item 含有可比公司快照和 `method1_replay_available=true`，但公告 PDF 不作为仓库资产提交。后续需要让 replay item 明确区分：

- 当前机器是否能按本地文件重建。
- 已提交快照是否可作为跨机器共享结果继续使用。
- 该快照是否来自人工择优合并。

### 2. replay 聚合文件和单样本缓存可能不一致

当前同步检查主要看代码列表、月份和缓存版本，不逐条校验：

- `replay_dataset.json` 内嵌 item。
- `replay_items/{code}.json` wrapper 内的 item。
- wrapper 的 `record_signature` / `pdf_signature`。

因此人工合并或跨机器合并后，可能出现聚合 item 和单样本 item 不一致，或者 item 内容和 wrapper 签名不完全表达同一个来源的情况。

### 3. 申购 history 的质量保护是必要的，但来源不够显式

`subscription_history_sample.csv` 会保留旧高质量行，这是正确保护；否则缺公告 PDF 时容易把完整样本降级成低信息样本。

风险在于：

- CSV 只保存结果字段，没有明确记录“本行为何保留旧行”。
- 合并时只能靠字段差异人工判断哪边更好。
- 与 replay item 的来源关系不够显式，导致同一代码可能在估值 replay 和申购 history 中呈现不同新旧状态。

### 4. 手工标签 CSV 混合自动列和人工列

`subscription_ladder_labels.csv` 现在既是人工输入文件，也是自动同步文件。

好处是用户打开一个表就能看到完整上下文；风险是：

- 自动列被不同机器刷新后容易产生合并冲突。
- 真正需要人工保护的只有 `manual_ladder` 和 `manual_note`。
- 自动列如果来自低质量 history，会影响“顶格抢时间”等人工标签解释。

## 八、建议的统一方案

短期不建议大改文件格式，建议先新增统一同步入口和同步报告：

- 新增 `tools/sync_offline_tuning_dataset.py`。
- 统一执行顺序：
  1. 检查 `首日分时走势/*.csv` 与 replay 代码列表。
  2. 构建或复用 `replay_items/*.json`。
  3. 重建 `replay_dataset.json` 聚合快照。
  4. 从 replay 派生 `subscription_history_sample.csv`，继续使用质量保护。
  5. 同步 `subscription_ladder_labels.csv`，保护人工列。
  6. 输出 `data/offline_tuning/sync_report.json` 或 `sample_manifest.json`。

`sample_manifest.json` 建议按代码记录：

- 是否存在本地分时 CSV。
- 是否存在 replay item。
- 是否进入 replay dataset。
- 是否存在申购 history 行。
- 是否存在手工标签行。
- replay item 的方法一可用状态、老股来源状态、可比公司来源状态。
- 申购 history 的质量分和是否保留旧行。
- 最后更新时间和是否人工择优合并。

中期再考虑拆分人工标签：

- 保留现有 `subscription_ladder_labels.csv` 兼容当前流程。
- 新增纯人工文件 `subscription_ladder_manual_labels.csv`。
- 同步命令生成带上下文的标签视图，减少人工文件中的自动列冲突。

长期目标：

- 所有调参入口默认只调用统一同步入口，不各自实现刷新逻辑。
- 所有可提交样本资产都带 schema、版本、来源和质量摘要。
- 跨机器合并时优先比较 manifest/同步报告，而不是直接靠大段 JSON/CSV diff 人工判断。
